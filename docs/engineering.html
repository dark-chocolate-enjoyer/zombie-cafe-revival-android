Implementation 01

Restoring music after game-state changes

Music could play when the cafe first loaded, then stay silent after a map visit, raid, or cafe reload.

Where the failure appeared

The Android bridge was capable of loading and starting an OGG file, so the first successful track made the audio system look healthier than it was. The important pattern only appeared over a longer session: once channel 0 had been used, later requests for cafe, map, or raid music stopped reaching Java playback.

Logcat showed the Java MediaPlayer becoming silent while the native game continued to report music as active. That mismatch directed the investigation away from damaged audio files and toward the native channel state.

Following the request through native code

Every music path eventually reached CCSound::StartMusic. The function stored its current track pointer at CCSound+0x34 and returned immediately when the requested pointer matched that value:

CCSound::StartMusic at 0x192f0a - original and patched Thumb
; original
192f0a  cmp  r0, r5          ; current track == requested track?
192f0c  beq  0x192f32     ; yes: return without reaching Java

; patched
192f0a  cmp  r0, r5
192f0c  nop              ; continue through stop/start handling

The comparison itself was reasonable, but the stored pointer was never cleared by the paths this build actually used. Java could finish, pause, or replace its player while native code continued to believe the old track was active. This caused two related failures:

  1. New starts were discarded.

    A later map, raid, or cafe request used channel 0 again and hit the early return.

  2. The cafe restart timer stayed closed.

    GameStateCafe::tick checked the same stale native belief before selecting another cue.

Changing the native playback gate

Replacing the early branch with nop allowed every explicit native start request to continue through the normal stop/start path. A second change was still required because GameStateCafe::tick called ZombieCafe::IsMusicPlaying before scheduling another track.

The call at 0x1235ca was redirected from CCSound::IsMusicPlaying to an 18-byte Thumb thunk placed in the unused javaFiksuRecordEvent body. The thunk first asks the native sound system, then calls javaIsMusicPlaying(0) only when native state is non-zero:

Retargeted call and gate thunk in the current native library
1235c8  push {r4, lr}
1235ca  bl   0x17e5c0     ; combined playback-state gate
1235ce  subs r3, r0, #1
1235d0  sbcs r0, r3

17e5c0  push {r4, lr}
17e5c2  bl   CCSound::IsMusicPlaying
17e5c6  cmp  r0, #0
17e5c8  beq  0x17e5d0       ; native says stopped: return false
17e5ca  movs r0, #0         ; channel 0
17e5cc  bl   javaIsMusicPlaying
17e5d0  pop  {r4, pc}
Why combine both states?

Using Java state alone would treat the menu track as cafe music during first entry. Using native state alone recreated the original stale-pointer bug. Requiring both keeps the original first-entry behavior while allowing a silent Java player to reopen the cafe timer.

The native cafe restart value was also made explicit instead of relying on the positional constants file. The first repair used 2,496 ms; the maintained library now writes 10,000 ms to ZombieCafe+0x2bc, giving the Java player time to finish before native code considers another cafe start:

GameStateCafe::tick restart interval in the current library
aef76  movw r1, #10000   ; restart interval in milliseconds
aef7a  ldr  r2, [r4, #12]  ; ZombieCafe object
aef7c  movs r3, #175
aef7e  lsls r3, r3, #2    ; 175 * 4 = 0x2bc
aef82  str  r1, [r2, r3]   ; cafe music timer = 10,000

Adding context to the Android bridge

Native code uses channel 0 for cafe, map, and raid music, so channel number alone cannot identify the screen. The Smali bridge adds mMusicMode with values 0=CAFE, 1=MAP, and 2=RAID. fromNative_loadMusic sets it from the filename requested by the native state machine. The normal raid cue is marked as raid and may be replaced with its alternate theme:

CC_Android.smali - mode classification inside fromNative_loadMusic
const-string v0, "Zombie Mini Cue 1g"
invoke-virtual {p1, v0}, Ljava/lang/String;->contains(...)Z
move-result v0
if-eqz v0, :mode_check_boss

const/4 v0, 0x2
sput v0, CC_Android;->mMusicMode:I  # RAID
invoke-static {}, Ljava/lang/Math;->random()D
# values below 0.5 replace p1 with "Zombie Mini Cue 1V2.ogg"

# "Haunted House" also sets RAID
# "Zombie Mini Cue 1V2" sets MAP when requested directly
# every other channel-0 filename sets CAFE

fromNative_startMusic then suppresses only a channel-0 start classified as map. This keeps map browsing silent without blocking raid music or channel-1 stings:

CC_Android.smali - map-only start suppression
if-nez p0, :map_ok
sget v2, CC_Android;->mMusicMode:I
const/4 v3, 0x1                     # MAP
if-ne v2, v3, :map_ok

const-string v3, "startMusic suppressed: map mode"
invoke-virtual {v2, v3}, PrintStream;->println(...)V
move v0, v1                         # report handled
goto :goto_0                        # do not start MediaPlayer

Finally, onCompletion was implemented for cafe mode. It rotates Zombie Theme V1 to Zombie Mini Cue 2g, then 3g, then back to V1. The next filename is held in mPendingCafeTrack and posted through a Handler after 0x61a8 milliseconds (25 seconds). run() rechecks that channel 0 is silent, loads the pending file, disables looping, and calls fromNative_startMusic(0).

CC_Android.smali - cafe completion scheduling and restart
const-string v2, "Zombie Mini Cue 2g.ogg"  # V1 -> 2g
# 2g -> "Zombie Mini Cue 3g.ogg"
# 3g -> "Zombie Theme V1.ogg"
sput-object v2, CC_Android;->mPendingCafeTrack:Ljava/lang/String;
const-wide/16 v2, 0x61a8                # 25,000 ms
invoke-virtual {v0, v1, v2, v3}, Handler;->postDelayed(...)Z

# Runnable.run(), after confirming cafe mode and silence
invoke-static {v2, v1}, CC_Android;->fromNative_loadMusic(...)Z
invoke-virtual {v1, v2}, MediaPlayer;->setLooping(Z)V
invoke-static {v2}, CC_Android;->fromNative_startMusic(I)Z

Ten OGG assets from the later Japanese build were added under assets/Music, including the three cafe cues, two normal raid cues, the Haunted House theme, and four stings. The existing .mp3-to-.ogg filename conversion in fromNative_loadMusic lets the recovered files satisfy the old native requests.

Checked by: repeated cafe-map-raid transitions, native call-site review, Android playback logs, post-patch disassembly, and APK rebuild/signature checks.

Implementation 02

Adding an offline cash-to-Toxin exchange to the Japanese build

The Japanese release no longer had a working route to its premium currency after the supporting services were retired.

Starting from the English implementation

Airyzz's earlier English patch repurposed four store entries that originally sold cash for Toxin. The item data was changed so cash became the purchase cost and the old “cash amount” field became the amount of Toxin to grant.

The Japanese furniture data supplied the first useful cross-build anchor. Rows 182 through 185 had the same Type-10 role and the same original pack values as the English build. That established what the store records represented, but not where the Japanese executable handled them.

JP rowOriginal packOffline exchange
18210 Toxin buys $10,000 cash$20,000 cash grants 10 Toxin
18325 Toxin buys $50,000 cash$50,000 cash grants 30 Toxin
184100 Toxin buys $250,000 cash$250,000 cash grants 175 Toxin
185350 Toxin buys $1,000,000 cash$1,000,000 cash grants 750 Toxin

Locating the Japanese purchase case

The Japanese native library retains dynamic C++ symbols. That made it possible to begin at GameStateCafe::completeStorePurchase(GameStateCafe*), whose Thumb function starts at 0x113710, instead of searching the entire library for a guessed byte pattern.

  1. Disassemble completeStorePurchase.

    The function selects purchase behavior through a jump table using the furniture record's Type value.

  2. Follow jump-table case 10.

    Type 10 resolves to the block beginning at 0x113b88, matching the four store records identified in the data.

  3. Trace the loaded fields.

    The block reads the Type-10 amount, loads the current cash wallet, adds the two values, and stores the result back to the same wallet field.

  4. Resolve the Toxin API separately.

    The exported symbol ZombieCafe::addToxin(int, bool) starts at 0x229fa0; getToxin and addToxin confirm the JP Toxin fields around offset 0x494.

Reading the original block

JP Type-10 case at 0x113b88
113b88  ldr  r2, [r4, #12]  ; ZombieCafe object
113b8a  ldr  r3, [r3, #88]  ; Type-10 amount
113b8c  ldr  r1, [r2, r6]   ; current cash
113b8e  adds r3, r1, r3     ; cash + amount
113b90  str  r3, [r2, r6]   ; store new cash
113b92  b    0x114126      ; common purchase exit

The register meanings were not inferred from names alone. They were established by following where each value came from and where it was reused:

ValueMeaningEvidence
r4Current GameStateCafe objectThe containing member function keeps its state pointer in r4; field [r4,#12] is repeatedly used to obtain the owning ZombieCafe instance.
r3 before 0x113b8aSelected furniture/store recordThe same record supplied the Type value used by the preceding switch. Offset #88 is the runtime amount consumed only by the Type-10 cash-pack case.
r6Cash-wallet field offset 0x67cr6 is loaded earlier from a literal containing 0x67c. The same field is used by nearby cash deduction and accounting paths.
r1 at 0x113b8cCurrent cash balanceIt is loaded from ZombieCafe + 0x67c, added to the pack amount, then written back to that exact field.

Why the English instruction patch could not be copied

The English implementation changed a direct wallet-field write from cash to Toxin. Its cash field is at offset 0x1ac. In the Japanese object layout, cash is at 0x67c and the main Toxin field is at 0x494. Copying the English bytes would therefore address unrelated Japanese state.

The safer JP patch calls the game's own Toxin function. Under the ARM calling convention, r0 holds the object pointer, r1 the integer amount, and r2 the boolean argument. The original block already provides the first two source values, so it can be replaced without adding a trampoline:

Patched JP Type-10 case - same 12-byte footprint
113b88  ldr  r0, [r4, #12]  ; this = ZombieCafe object
113b8a  ldr  r1, [r3, #88]  ; amount = BuyMoneyAmount
113b8c  movs r2, #0         ; direct offline credit
113b8e  bl   0x229fa0     ; ZombieCafe::addToxin(int, bool)
113b92  b    0x114126      ; preserve common exit

Calling addToxin also preserves the Japanese game's own wallet update and clamping logic. The boolean is set to false to match the direct-credit behavior of the earlier offline exchange rather than pretending a server-backed Toxin purchase occurred.

Checked by: exact source-byte guards, post-patch disassembly confirming the branch target, all 835 furniture records reaching exact EOF, a byte-identical pack/unpack/repack cycle, and APK archive/alignment/signature inspection.
