Music playback repair

Music played on first load but often stayed silent after entering the map, a raid, or another cafe.

Native playback state

Logcat showed that Java's MediaPlayer had stopped while native code still reported channel 0 as active. Tracing the request led to CCSound::StartMusic, where a stale track pointer caused an early return. Replacing that branch with nop lets explicit start requests reach the normal stop/start path.

libZombieCafeAndroid.so - CCSound::StartMusic at 0x192f0a
; original
192f0a  cmp  r0, r5          ; current track == requested track?
192f0c  beq  0x192f32     ; return without reaching Java

; patched
192f0a  cmp  r0, r5
192f0c  nop              ; continue into stop/start handling

The cafe restart check also needed real Java state. Its call was redirected to a small Thumb thunk in unused native space. The thunk returns true only when both the native sound system and Java player report playback.

Combined native/Java playback gate
1235ca  bl   0x17e5c0     ; redirected cafe check

17e5c0  push {r4, lr}
17e5c2  bl   CCSound::IsMusicPlaying
17e5c6  cmp  r0, #0
17e5c8  beq  0x17e5d0
17e5ca  movs r0, #0         ; music channel
17e5cc  bl   javaIsMusicPlaying
17e5d0  pop  {r4, pc}

Android bridge changes

Channel 0 carries cafe, map, and raid music, so CC_Android.smali now records the requested context as CAFE, MAP, or RAID. Map starts are suppressed without blocking raids. Cafe completion schedules the next track after 25 seconds.

CC_Android.smali - context and cafe rotation
# classify the normal raid cue
const-string v0, "Zombie Mini Cue 1g"
invoke-virtual {p1, v0}, Ljava/lang/String;->contains(...)Z
const/4 v0, 0x2
sput v0, CC_Android;->mMusicMode:I  # RAID

# on cafe completion: V1 -> 2g -> 3g -> V1
sput-object v2, CC_Android;->mPendingCafeTrack:Ljava/lang/String;
const-wide/16 v2, 0x61a8       # 25,000 ms
invoke-virtual {v0, v1, v2, v3}, Handler;->postDelayed(...)Z

Result: cafe music rotates again, raid themes play in raids, map browsing remains silent, and ten missing OGG files are supplied from the later Japanese build.

Japanese cash-to-Toxin exchange

The Japanese client lost access to premium currency when its purchase servers closed. Four old cash-pack entries were converted into local cash-to-Toxin exchanges.

Finding the purchase handler

  1. Matching Type-10 furniture rows identified the same four store packs used by the English exchange.
  2. The symbol GameStateCafe::completeStorePurchase led to the JP purchase switch at 0x113710.
  3. Jump-table case 10 led to 0x113b88, where the selected amount was added to the cash wallet.
Original JP Type-10 case
113b88  ldr  r2, [r4, #12]  ; ZombieCafe object
113b8a  ldr  r3, [r3, #88]  ; selected pack amount
113b8c  ldr  r1, [r2, r6]   ; current cash
113b8e  adds r3, r1, r3
113b90  str  r3, [r2, r6]   ; write cash
113b92  b    0x114126

The register meanings came from data flow, not guessed names:

RegisterMeaningEvidence
r4GameStateCafe[r4,#12] repeatedly loads the owning game object.
r3Selected store rowThe same pointer supplied Type 10 to the switch; offset 88 supplies its amount.
r6Cash offset 0x67cThe surrounding deduction and accounting paths use the same field.
r1Current cashLoaded from, added to, and written back to ZombieCafe+0x67c.

Applying the Japanese patch

The English instruction bytes could not be copied because its object offsets differ. The JP patch instead calls the exported ZombieCafe::addToxin(int, bool) at 0x229fa0, using the selected store amount already available in the case.

Patched JP Type-10 case - same 12-byte footprint
113b88  ldr  r0, [r4, #12]  ; this = ZombieCafe
113b8a  ldr  r1, [r3, #88]  ; Toxin reward
113b8c  movs r2, #0         ; direct local credit
113b8e  bl   0x229fa0     ; addToxin(int, bool)
113b92  b    0x114126      ; original common exit

Result: the four shop entries deduct their configured cash prices and grant 10, 30, 175, or 750 Toxin entirely within the offline client.
